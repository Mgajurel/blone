# PRD — Blone: a frictionless second brain

> **Triage:** `needs-triage` — tracked as markdown issues in `.docs/issues/` (this project's file-based tracker; no Linear/Jira).
>
> **Working name:** "Blone" (from the project directory); rename freely.

## Glossary

- **Save / capture** — the act of pressing the hotkey; produces a bookmark (URL) or text note in Karakeep.
- **Type** — exactly one value from a closed set (`tweet`, `article`, `product`, `design`, `video`, `link`) describing what kind of thing a save is. The browse axis.
- **Topic tags** — 2–5 freeform tags generated by the local model. The search axis.
- **Archive (read-state)** — Karakeep's "tucked away / done" state for a bookmark (the `e` key). *Not* a page copy.
- **Offline snapshot** — a stored full-page HTML copy or screenshot. Off by default in this product; distinct from archive (read-state).
- **Extracted text** — readability-parsed plain text of a saved page. Always stored; powers search and tagging.

## Problem Statement

I constantly encounter things worth keeping — tweets, Hacker News posts, products I like, designs I admire, fragments of text — while scrolling in a browser. Every existing way to keep them either demands a decision at save time (where to file it, what to call it) or scatters the material across bookmarks, likes, and notes apps where it is never found again. Because saving has friction, I save less; because retrieval is weak, what I do save might as well be lost. I want the act of keeping something to cost one keystroke, and the act of finding it months later to cost one search — so that over time an effortless, searchable second brain accumulates on hardware I control.

## Solution

A single keystroke (`cmd+opt+s`) in the browser silently captures the current page — or the selected text — into a self-hosted pipeline that categorizes it automatically: a deterministic rule or a local LLM assigns exactly one *type*, the local LLM adds freeform *topic tags* and a one-line summary, and the page's extracted text is stored so its full content is searchable. A custom web app — keyboard-driven, dense, terminal-flavored (Omarchy feel) — presents everything as a reverse-chronological feed with an ever-present instant search bar and a command palette. Correction (fixing a type, editing tags) costs one keystroke on a surface visited daily, never a decision at capture time. Everything runs locally on one Mac: Karakeep + Meilisearch + a headless-Chrome crawler in Docker, Ollama for inference, zero cloud calls.

## User Stories

1. As a user mid-scroll on a tweet's permalink page, I want to press `cmd+opt+s` and keep scrolling, so that keeping something costs me no attention.
2. As a user who just pressed the capture hotkey, I want a small toast confirming the save, so that I trust the capture happened without looking away from what I was reading.
3. As a user who has selected text on a page, I want the same hotkey to save that selection as a text note with the source URL attached, so that the exact passage I cared about is preserved even if the page later changes or dies.
4. As a user on a page with nothing selected, I want the hotkey to save the page URL itself, so that one shortcut covers both "keep this quote" and "keep this page".
5. As a user with a stray thought not attached to any page, I want a "new note" action in the app's command palette, so that free-floating text can enter the same brain as web captures.
6. As a user who saves things, I want the pipeline to fetch each saved URL and store its title, description, favicon, and extracted plain text automatically, so that a bare URL becomes a described, searchable object with no work from me.
7. As a user saving from well-known domains, I want the type assigned deterministically by URL rules (x.com → `tweet`, youtube.com → `video`, …), so that the browse axis is perfectly reliable wherever a rule can decide.
8. As a user saving a product or design page on an arbitrary domain, I want the local model to guess the type from the extracted text, so that even rule-less saves land in a browsable category.
9. As a user reviewing my feed, I want to cycle a wrong type with a single keystroke (`t`), so that correcting the machine costs less than filing by hand ever would.
10. As a user who saves things, I want the local model to attach 2–5 freeform topic tags to each save, so that topical retrieval works without me ever naming a topic.
11. As a user scanning my feed, I want a one-line AI summary on each card, so that I can recognize a save without opening it.
12. As a privacy-conscious self-hoster, I want all inference to run on my own machine via Ollama, so that nothing I save is sent to a third-party model provider.
13. As a user opening the app, I want a reverse-chronological feed of my captures as dense cards (type badge, title, summary, favicon + domain, topic tags, age), so that re-encountering old saves happens naturally.
14. As a keyboard-driven user, I want `j`/`k` to move a visible selection through the feed instantly, so that navigating feels like a TUI, not a webpage.
15. As a keyboard-driven user, I want `Enter` to open the selected save's detail and `o` to open its source URL in a new tab, so that revisiting the live web is one keystroke away.
16. As a user done with a save, I want `e` to archive it (read-state), so that the feed stays a living stream rather than a landfill, while archived items remain searchable.
17. As a user hunting for something, I want `/` to focus an ever-present search bar with results appearing as I type, so that search feels instant and free.
18. As a user hunting for something, I want full-text search over extracted page text — not just titles — with typo tolerance, so that I can find a page by a phrase I half-remember from its body.
19. As a power searcher, I want query qualifiers (`#tag`, `type:design`, `url:`, `after:`/`before:`, `is:archived`) passed through to the search engine, so that I can slice the brain precisely, Hister-style.
20. As a user browsing by kind, I want one-keystroke type filters (all products, all designs, all tweets), so that the type axis I paid for is a first-class view.
21. As a keyboard-driven user, I want a command palette (`cmd+k`) exposing every action — search, type filters, new note, open source, archive, settings — so that no feature requires a mouse or a menu hunt.
22. As a curator, I want an inline tag editor on the selected card (add, remove, rename tags), so that tag soup can be pruned the moment I notice it.
23. As a user with evolving taste, I want to delete a save entirely, so that regret is reversible.
24. As a user of a young product, I want an empty state that tells me the capture hotkey, so that the first-run experience teaches the core loop.
25. As a user who lives in this app, I want a bottom status line showing item count, the active filter, and key hints, so that state and affordances are always visible, waybar-style.
26. As a user with strong aesthetic preferences, I want the whole UI dense, monospace, flat, and dark (Tokyo-Night-flavored), so that the app feels like part of my terminal environment, not a SaaS dashboard.
27. As a self-hoster, I want the entire stack to start with one `docker compose up` plus a running Ollama, so that setup is a copy-paste, not an evening.
28. As a self-hoster, I want offline snapshots (full-page HTML, screenshots) OFF by default but exposed as configuration, so that my storage stays lean while the option remains discoverable in the app's settings surface.
29. As a self-hoster, I want the app to function entirely on localhost with no external dependencies at runtime, so that the brain works on a plane and never phones home.
30. As a self-hoster, I want my data to live in Karakeep's standard storage (one SQLite DB + assets directory), so that backup is a file copy and exit is Karakeep's own export.
31. As a user whose saves fail sometimes (crawler down, X blocking the fetch), I want the save preserved with whatever was captured (URL, selection) and visibly under-enriched rather than dropped, so that capture never silently loses anything.
32. As a user watching the machine, I want rule-derived types to take precedence over model-guessed types (and my manual choice to beat both), so that the most reliable source of truth always wins.
33. As a future tinkerer, I want the tagging model and prompt to be swappable via configuration, so that a better local model — or a cloud escape hatch — is a config change, not a rewrite.

## Implementation Decisions

**Architecture.** Thin custom UI over reused infrastructure. Karakeep (with Meilisearch and its headless-Chrome crawler, via docker-compose) is the entire backend: storage, crawling, text extraction, tag storage, search indexing, and its REST API is the only boundary the custom code talks to. Ollama runs natively on the host Mac and is wired into Karakeep's inference config with a custom tagging prompt. Nothing custom persists data; there is no bespoke database or schema.

**Modules to build (five).**
- *karakeep-client* — a typed wrapper over Karakeep's REST API exposing the app's whole vocabulary (`search`, `saveNote`, `setType`, `updateTags`, `toggleArchive`, list/paginate, delete). Encapsulates auth, pagination, and API quirks; every other module and component depends on it and never on raw HTTP. The interface is intentionally small and stable so Karakeep upgrades are absorbed here.
- *query-compiler* — a pure function translating palette/search input with qualifiers into Karakeep search API parameters. No I/O.
- *type-ruler* — a pure function mapping a URL to a type or "no rule" (meaning the model's guess stands). Deployed first as Karakeep rules-engine configuration; the pure function becomes a tiny webhook service only if the built-in rules engine proves insufficient. The rule table is data, not code.
- *capture-logic* — the custom browser extension's pure core: given (selection, page URL, page title), produce the save payload — selection present → text note with source URL; otherwise → page bookmark. The extension shell around it is a thin MV3 wrapper calling the Karakeep API.
- *command-engine* — the keymap table and palette action registry (navigation, archive, retag, filters, new note), decoupled from React components so bindings are declarative and inspectable. React components stay shallow on top of these five.

**Type representation.** Types are stored as Karakeep tags under a reserved prefix (e.g. `type/design`). Precedence when multiple type tags exist: manual > rule-derived > model-guessed; the UI displays exactly one winner and offers a fixup affordance when it detects conflict. The tagging prompt instructs the model to emit its type guess in this namespace plus 2–5 plain topic tags.

**Capture path.** v0 binds Karakeep's stock browser extension to `cmd+opt+s` (page saves, silent). The custom selection-aware extension replaces it within the same big-bang build. Known contract: tweets are captured from their permalink page or via selected text; a mid-timeline save captures the timeline URL (a later extension enhancement may resolve the focused tweet's permalink from the DOM).

**Enrichment pipeline.** Karakeep's crawler fetches every saved URL; extracted plain text is always stored (it feeds both the search index and the tagging model). Offline snapshots (full-page HTML archive, screenshots) are disabled by default via deployment configuration; the settings surface exposes the current pipeline configuration and, where the API permits toggling, toggles it — otherwise it documents the config change. AI one-line summaries are enabled via Ollama.

**Search.** Entirely inherited: Meilisearch full-text over titles, extracted text, notes, and tags, with Karakeep's query qualifiers passed through verbatim by the query-compiler. No custom index, no embeddings, no vector store in v0.

**UI.** Vite + React + Tailwind single-page app served locally, using cmdk for the palette; talks to Karakeep's API through a trivial local proxy (CORS). One screen: ever-present search bar, reverse-chron feed of dense cards, bottom status line, palette overlay. Full keyboard map: `/` search, `j`/`k` move, `Enter` detail, `o` open source, `t` cycle/fix type, `e` archive, `cmd+k` palette. Visual system per `design.md` (Tokyo-Night-flavored, monospace, flat, dense; one dark theme in v0).

**Deployment.** Single Mac, pure localhost. docker-compose for Karakeep + Meilisearch + headless Chrome; native Ollama (~8B model, e.g. `qwen3:8b`). No auth hardening beyond localhost binding; single user.

**Build order.** Big bang by explicit choice: pipeline + custom extension + full UI assembled before daily use begins. Accepted mitigation: push ~20 real URLs through the pipeline early during assembly to smoke-test tag quality while the UI is still being built.

## Testing Decisions

**What makes a good test here:** assert external behavior only — given this input, this output — never internal call sequences or intermediate state. Pure modules make this natural: no mocks, no rendering, no network. A test that would break under a refactor that preserves behavior is a bad test.

**Modules under test (per decision): the four pure-logic modules.**
- *query-compiler* — qualifier parsing (`#tag`, `type:x`, `after:`/`before:`, `is:archived`, bare terms, combinations, malformed input passes through as plain text).
- *type-ruler* — the rule table (known domains → types, subdomain/path variants, unknown domains → "no rule").
- *capture-logic* — selection → text-note payload with source URL; no selection → page bookmark; edge cases (empty-whitespace selection, missing title).
- *command-engine* — keymap dispatch (key → action, modifier handling, no dispatch while an input is focused).

**Not under test in v0:** karakeep-client (exercised constantly by real use against a live local API; fixture tests deferred until a Karakeep upgrade first bites), React components (manual daily use is the harness).

**Prior art:** none — greenfield. Harness is vitest with tests colocated next to each module; this PRD establishes the convention.

## Out of Scope

- **Phone capture / remote access** — no Tailscale, no mobile app wiring; desk-only capture is accepted. Bolt-on later without redesign.
- **Semantic retrieval** — no embeddings, no vector store. Named upgrade path when FTS demonstrably fails: connect Karakeep's MCP server to an LLM client first (zero build), vector sidecar only after that.
- **Spatial canvas** — no freeform arrange-things board; feed + palette is the surface. Revisit only if arranging ever proves necessary.
- **Offline snapshots by default** — full-page HTML and screenshots stay off; the declined screenshots-for-designs exception stays declined.
- **Multiple themes / light mode** — one dark theme ships.
- **Passive browsing index (Hister-style)** — deliberate saves only; Hister can run beside this system later without conflict.
- **Multi-user, auth, sharing** — single user on localhost.
- **Cloud tagging** — local-only inference, with the documented one-line config escape hatch to a cloud model if quality disappoints.
- **OS-wide capture (Raycast/Hammerspoon), always-on home box, VPS, stats/graph views** — all deferred.

## Further Notes

**Consciously accepted risks** (from the design interview, so nobody is surprised later):
1. Local ~8B tagging is noisier than cloud; the type axis is protected by rules + one-keystroke veto, and the cloud escape hatch is a config flip.
2. No pixels: a deleted tweet or redesigned page survives only as extracted text.
3. Phone-moment captures leak out of the brain until remote access is added.
4. Big-bang build means nothing is validated by real use until assembly finishes; the 20-URL smoke test during assembly is the pressure valve.
5. Coupling to Karakeep's data model is accepted; its export is the exit.

**Terminology hazard:** Karakeep's "archived" means read-state (done), not page copy. This PRD and the UI use *archive* strictly for read-state and *offline snapshot* for page copies.
